# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Stronghold is an open-source inventory/stock tracking tool for small and medium businesses (SMBs). It is single-user and pre-1.0.

## Architecture

A Python domain core with a thin FastAPI JSON layer (`backend/`) and a SvelteKit
SPA (`frontend/`) -- see ARCHITECTURE.md for the full design. The core is
UI-agnostic (no web-framework imports), which is what made the frontend swappable.

Two invariants the file layout does not show:
- `db.py` owns every write (`@_write`: one transaction, logged, re-exports the
  `.sql` on success; validation failures raise `InventoryError`). `api.py` owns
  no domain logic -- it only shapes requests/responses and maps `InventoryError`
  to HTTP 400.
- Detail pages cross-link heavily to related entities. Reverse lookups needing a
  join have a dedicated route -- `GET /parts/{id}/purchase-orders`,
  `/parts/{id}/used-in`, `/parts/{id}/builds|consumed-by`,
  `/suppliers/{id}/parts|purchase-orders`,
  `/supplier-parts/{id}/purchase-orders`; everything else filters an existing
  list client-side.

## Design decisions

- The project was a plugin-based command-log kernel (event sourcing, then snapshot undo/redo) until 2026-07; it was deliberately collapsed to this monolith to iterate on real features first. The old design lives in git history; refactor toward it only when a real feature demands it (e.g. bring the command log back the day a booking needs undo), not speculatively.
- The state tables are the truth; `inventory.sql` (rewritten after every mutation: a `CREATE TABLE IF NOT EXISTS` plus one INSERT per row, per table) is the backup/recovery story so the data can live in git. It is self-contained -- restore into an empty db with `sqlite3 inventory.db < inventory.sql`.
- No schema migrations yet (alpha): `db.init` runs `create_all`, which only creates missing *tables*, never alters existing ones. Adding/changing a column does not update an existing `inventory.db` (queries fail with `no such column`); the fix during prototyping is to delete `inventory.db` and recreate it. Data migration is 1.0 work. See ARCHITECTURE.md "Deliberate simplifications".
- No hard deletes. Parts, suppliers and supplier parts carry an `active` flag (deactivated, never removed; UIs hide inactive by default). Purchase orders and build orders have no `active` flag -- their `status` field carries lifecycle state (e.g. `Cancelled`, `Complete`). Stock items likewise use `status` instead of `active`: `Available` or `Consumed by build order` -- stock never disappears (see build consumption below). Plain FKs, no cascade. PO lines and BOM lines are order/build detail: plainly removable (a PO line only if not booked).
- Every master record has an integer PK (`Part`, `Supplier`, `SupplierPart`, `PurchaseOrder`, `StockItem`, `POLine`, `BuildOrder`): a local max+1 id in normal use, but the InvenTree pk copied verbatim during migration (the db is empty then, so ids stay traceable back to InvenTree). `sku` (on `Part` and `SupplierPart`) is a plain human code, not unique. `Part.assembly` marks a part built from others; its components live in `BomLine(parent_part_id, component_part_id, quantity)` (float qty, unique per parent+component). `Part.virtual` marks a part with unlimited stock (e.g. labour): it never has a stock item, is only used for BOM pricing, and builds never consume it; `assembly` and `virtual` are mutually exclusive (validated in `set_part_assembly`/`set_part_virtual`). A `PurchaseOrder` has a `supplier_id`; its `reference` and `start_date` are both NOT NULL and defaulted in `create_po` (to `PO-<pk>` zero-padded to 4, matching the imported codes, and to today) -- `start_date` is the sort key for "latest price", so a dateless order could never win it, and `edit_po` rejects blanking either. A `POLine` references a `supplier_part_id` (whose supplier must match the PO's) and tracks `received` (ordered units received into stock); `edit_po_line` changes its quantity and/or price, repricing the part and any stock booked against that line. Receiving a line (`book_po_line`) creates a stock item counting `received_qty * supplier_part.pack_qty` (a line orders packs; each holds `pack_qty` items), stamps that stock's `po_id`, increments the line's `received`, and adds a `Booking` row -- all in one transaction. `StockItem.count` is float (parts may be measured, e.g. kg/m); `StockItem.po_id`/`StockItem.build_id`/`StockItem.consumed_by_build_id` are nullable FKs to the PO it was received against / the build that produced it / the build that consumed it (separate columns: assembly output produced by one build and eaten by another is both, and collapsing them loses the producing link). Over-receiving (received > ordered) is allowed. Money is float.
- A `BuildOrder(part_id, quantity, status, ...)` is the assembly analogue of a PO: it builds an assembly `Part` (which must have `assembly=True`). `quantity` is an int -- assemblies are whole, no partial builds (produce quantity is likewise int). It is produced incrementally: `produce_build(build_id, qty)` reads the build's **`BuildLine` snapshot** -- the part's BOM copied onto the build at creation, so editing the BOM afterwards never rewrites what an existing build consumes; the snapshot also carries `unit_price` for virtual components only (never consumed, so nothing else records the labour rate the build was costed at), falling back to the part's current estimate when null; the InvenTree import stamps it from the part's price of the day, since InvenTree stores no price on `/build/line/` and its `bom_item` pricing is live, not historical -- and, in one transaction, consumes components FIFO for exactly `qty` units then produces one Available stock item of the assembly counting `qty` and stamped `build_id`. Consumption never destroys stock: a source Available item's count drops by the amount taken and a matching `Consumed by build order` item (also stamped `build_id`, and carrying the source's `po_id` for price provenance) is split off -- so what was used, and the price it was bought at, stay traceable (the basis for recalculating produced cost). Virtual components hold no stock, so nothing is drawn down, but a `STOCK_CONSUMED` row is recorded for them at the build line's snapshotted rate (`PriceBasis.VIRTUAL`) so the labour shows in the consumed table and counts in `build_unit_cost`; being consumed rows they never enter the stock value total. Shortages do not block production: a short component is drained to zero and the missing quantity is put on credit -- a `STOCK_CONSUMED` row at the part's estimate (so the assembly is costed in full rather than as a floor) plus a **negative-count `STOCK_AVAILABLE` row** stamped `consumed_by_build_id`, written as an adjacent id pair (consumed first). This is the one place Available stock goes negative; the debt nets out of on-hand sums and is deducted from the stock value report. `produce_build`'s FIFO select therefore filters `count > 0` -- consuming a debt row would invert the arithmetic. Booking the missing parts on a PO settles it (`_settle_stock_debt`, called from `book_po_line`): the debt shrinks, the paired consumed row is stamped with the PO and repriced to what was paid (splitting if the receipt only covers part of it), the settled units never reach the shelf, and the build's produced stock is repriced off the now-real cost. Debt rows settle to zero rather than being deleted; the settled receipt row also ends at zero (its units went straight into the assembly and it must survive because it carries the `Booking`), so the stock tables carry a `nonzero` bool filter hiding zero-count rows by default -- do not "fix" those zeros by keeping counts on the shelf, that double-counts against the assembly they went into. The user chose to produce anyway; the frontend surfaces the shortfall in the produce dialog. `produced_qty(build_id)` sums every row the build produced (not just Available ones -- output sold on or eaten by a later build is still output), floored at `BuildOrder.imported_produced` (InvenTree's own `completed` count, imported because InvenTree deletes fully-used stock, so surviving rows cannot reconstruct history); when cumulative production reaches `build.quantity` the status flips to `Complete`. Producing more than remaining is rejected, as is lowering `quantity` below what's already produced. Status transitions are constrained in `edit_build`: `Complete` only when produced equals quantity, and once anything is produced the order is locked to `Production`/`Complete` (no reverting). The produce button in the UI shows only when `status == "Production"`; the status dropdown greys out disallowed transitions. `BuildStatus` is mostly InvenTree's labels with two departures: `Draft` (ours -- the status `create_build` defaults to via `BuildOrderIn`, a scratchpad that books no demand) and no `On Hold`, which the InvenTree import folds into `Pending`. Demand (`db.part_demand`, see below) counts `Pending` and `Production` builds; because the frontend validator generator keys enum picklists by field name (last write wins), PO, build and stock `status` collapse into one generated `STATUS_OPTIONS` -- stock's wins -- so both the PO and build picklists are hardcoded in `frontend/src/lib/status.ts` (`PO_STATUS_OPTIONS`/`BUILD_STATUS_OPTIONS`), never imported from `validators.ts`. Any new DTO with a `status` field silently changes which one wins.
- InvenTree import is a one-shot migration, not a product feature. `backend/migrate_inventree.py` (run `uv run python migrate_inventree.py <url> <user> <password>`) drops the db and rebuilds it: parts, BOM, suppliers, supplier-parts, purchase orders (cancelled ones and their lines dropped), PO lines, build orders (cancelled dropped), each build's component snapshot (InvenTree `/build/line/`, whose extended quantity is divided by the build quantity to give our per-unit `BuildLine`; virtual components get `unit_price` baselined at the part's current price, as InvenTree has no historical rate to import), the stock each build consumed (InvenTree's `?consumed=true` stock, imported as `STOCK_CONSUMED` rows stamped `build_id` so historical builds can be costed) with produced stock back-linked from InvenTree's own `build` field on the stock row, and available stock (fetched directly, not replayed as bookings). Every InvenTree pk is copied as our pk, so no remap and no `inventree_id` column. Rows whose FK targets are missing (or fractional stock qty) are skipped/rounded with a printed report; a fractional build-order quantity is bad data (assemblies are whole) and aborts the import with an error rather than being rounded. `backend/inventree.py` is the read-only HTTP client it uses.
- Settings split by one test: does a wrong value stop the app running/being reachable? Deployment settings live in `settings.toml` (`settings.py`); domain settings (GUI title, stocktake reason lists) are data in the `settings` table (`db.DOMAIN_DEFAULTS`, `db.get_setting`/`db.set_setting`), edited on `/settings`. A setting holding a list is one comma-separated string (`stocktake.add_reasons`/`subtract_reasons`), parsed by the route that serves it (`GET /api/settings/stocktake-reasons`) rather than by the frontend. The whole InvenTree connection (url/username/password) goes in `settings.toml`, never the database: `inventory.sql` is tracked in git.
- `PartOut` carries four derived quantities, none of them cached: `in_stock` (a grouped sum of `STOCK_AVAILABLE` counts, so debt rows net out), `needed` and `incoming` from `db.part_demand`, and `suggested_order` = `max(0, needed - in_stock - incoming)`. `part_demand` is two grouped queries plus one `produced_qty` per open build: demand is each `Pending`/`Production` build's `BuildLine` per-unit quantity times its units left to produce (virtual components excluded -- they hold no stock); incoming is `(POLine.quantity - received) * pack_qty` over non-terminal PO statuses. The part page's purchase dialog prefills packs as `ceil(suggested_order / pack_qty)` *per supplier part*, since pack sizes differ.
- `Part.estimated_price` is a cached unit price (`price_partial` flags an incomplete BOM), computed in `db.py`'s pricing section, not in `api.py`. A virtual part's price is hand-set (`set_part_price`, PATCH `estimated_price`; rejected for non-virtual parts, and `patch_part` uses `model_fields_set` so an explicit null clears it) and returned as-is by `_compute_price`; a non-virtual, non-assembly part is worth `latest_po_unit_price` (the newest non-cancelled PO line pricing it, `price / pack_qty`, ordered by `PurchaseOrder.start_date` -- ids do not follow date order); an assembly is the recursive sum of its BOM components. `POLine.price` is not nullable, so `0` means "not filled in" and never counts as a price. The cache is refreshed inside the transaction of every write that can change it (`add_po_line`, `remove_po_line`, the BOM writes, `edit_supplier_part`, `set_part_assembly`, `edit_po`) via `refresh_part_price`, which walks *up* to every containing assembly; `refresh_all_prices` (POST `/api/parts/refresh-prices`, and once in `main.create_app` at startup) is the backfill path, covering rows written outside the app.
- `StockItem.unit_price` is a *separate* cache from `Part.estimated_price` and the two differ by design: stock is worth what its own order paid, the part is worth its latest price. `db.refresh_stock_price` resolves one item -- its PO (the booked line, else that order's line for the same part) first, then its producing build (`build_unit_cost`: the sum of what that build's `STOCK_CONSUMED` rows were worth, divided by `max(produced_qty, build.quantity)` -- output gets sold on, so surviving units must not inherit the whole batch cost), then the part estimate, recording which in `StockItem.price_basis` (`models.PriceBasis`: `po`/`build`/`build_partial`/`estimate`/`po_no_price`/`none`; `build_partial` means a consumed input was itself estimated -- which covers a shortage, since the missing quantity is consumed at the part's estimate until the parts are received). Refreshed by the writes that create or reprice stock (`book_po_line`, `book_po`, `create_item`, `produce_build`) and by `refresh_part_price` for every part it touches. The stock value report is a plain read of these columns -- it owns no pricing logic. Its `total`/`unpriced` cover `STOCK_AVAILABLE` rows only: consumed rows are build inputs already counted inside the assembly they became, so summing them would double-count (they stay in `rows` for provenance). BOM cycles are not blocked on write (see `add_bomline`), so the recursive walk carries a path-scoped `seen` guard.
- Assemblies are built, not purchased: `create_supplier_part`/`edit_supplier_part` reject an assembly part, and `set_part_assembly` rejects a part a supplier already sells. `Part.purchasable` (default true) is the manual version of the same gate -- `_check_purchasable` rejects a supplier part for an assembly *or* a part flagged non-purchasable, so only a purchasable part can reach a PO.
- Every write can append an `Activity` row (`db._activity`, inside the caller's transaction so it commits atomically), surfaced by `GET /api/activity` and the `/activity` page. `refs` is a JSON list of `{type, id, label}` for cross-linking. Coverage is uneven by design -- some setters log, others do not; add a call where the audit trail matters.
- Deliberate shortcuts are marked with `ponytail:` comments naming the ceiling and upgrade path.

## Commands

- `uv run pytest` -- run backend tests (`backend/test_domain.py` + `backend/test_api.py`)
- Frontend needs Node 20+ (Node 18 builds but is unsupported); the dev server proxies `/api` to :8080
- Prod (single process): build the frontend, then `cd backend && uv run main.py` serves API + SPA on :8080. Running `uvicorn main:app` directly skips `db.init`, so the API 500s -- use `main.py`
- Frontend DTO types + validators are generated from the backend: `cd frontend && npm run gen:types` regenerates `backend/openapi.json` from the live routes (`backend/export_openapi.py`), then writes `frontend/src/lib/api-types.ts` (openapi-typescript) and `frontend/src/lib/validators.ts` (valibot schemas via `scripts/gen-validators.mjs`). `src/lib/types.ts` is thin friendly aliases over api-types; form validation uses the valibot schemas through `src/lib/validate.ts`. After changing any DTO or adding a Pydantic `Field(...)` constraint in `backend/api.py`, run `gen:types` -- validation rules live in the Pydantic models only. `openapi.json` is gitignored (a build artifact); `api-types.ts`/`validators.ts` are committed so the frontend builds without a live backend.
- Navigate the two big backend files by section banner, don't read them whole: `grep -n '^# --' backend/db.py` (or `api.py`) is a working table of contents. Two traps: five Pydantic models sit *outside* `api.py`'s `# -- schemas` section, so `grep -n '^class .*BaseModel' backend/api.py` is the reliable way to find them all; and `db.py`'s `set_part_assembly`/`set_part_virtual`/`set_part_purchasable`/`set_part_price` live under `# -- bom`, not `# -- parts`.
- A tracked pre-commit hook (`.githooks/pre-commit`) blocks commits with stale generated files when any `backend/*.py` (not just `api.py` -- `models.py` holds the StrEnums that become picklists), `api-types.ts`, or `validators.ts` is staged. It is not active in a fresh clone -- enable once with `git config core.hooksPath .githooks`.
- CI (`.github/workflows/ci.yml`) runs on every PR: `pytest`, `ruff check`, `ruff format --check`, `npm run check` (svelte-check), and `npm run check:types-fresh`. That last one regenerates from the live routes and fails on any diff, so stale generated types are caught whichever backend file caused the drift.
- Secrets (InvenTree URL/username/password for `migrate_inventree.py`) live in `SECRETS.md` at the repo root (gitignored). Read credentials from there when a task needs them; never commit, echo, or otherwise expose the file's contents.

## Running the app for manual verification

- Free port 8080 before restarting: `ss -ltnp | grep :8080` for the pid, then `kill -9 <pid>`. Never `pkill -f main.py` -- it can kill the agent's own process tree.
- The frontend renders client-side (SPA), so a 200 on `/parts` only proves the SPA fallback served. **Exercise real flow via the API** (`curl /api/parts`, POST/PATCH) and/or drive the DOM with the browser tools -- screenshots may be flaky, so read state via the JS tool (`document.querySelectorAll('tbody tr').length`, `.rowcount`).
- The API is the contract: `curl http://localhost:8080/api/...` is the fastest proof a change works end-to-end.

## Testing

- Pre-1.0 (no tags yet), so the user-wide coverage rule resolves to happy-flow only -- not 100% line/branch coverage as a goal in itself. Revisit at 1.0.
- Do not add edge-case tests speculatively. Add one only after a real bug is found there, to prevent regression.
- Frontend correctness is checked with `npm run check` (svelte-check) and by driving the running app -- there is no frontend test runner.
- Backend lint/format is ruff (`uv run ruff check backend`, `uv run ruff format backend`), config in `pyproject.toml`. `S`/`BLE` are enabled because the codebase carries `noqa` for them; `DTZ011` is off (PO `start_date` is a calendar sort key, not an instant). Both are CI gates, so run them before committing.

## Precedence

The user-wide `~/.claude/CLAUDE.md` sets general coding conventions (Python style, git workflow, etc.) and applies here too. Where this file conflicts with it, this file wins.

## Commits
Never commit to `main`. Every change goes on a feature branch and reaches
`main` through a PR (`gh pr create`) -- see the README's Contributing section.
Commit isolated changes one by one. Still pre-1.0, so breaking changes are
allowed, but name them in the PR description.
