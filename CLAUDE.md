# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Stronghold is an open-source inventory/stock tracking tool for small and medium businesses (SMBs). It is single-user and released (1.0). The user-wide rule that permits unannounced interface changes below 1.0 no longer applies: breaking changes to the API, CLI flags or output formats need a major bump and must be named in the PR description. Data files carry a schema version and are migrated on open (see below).

## Architecture

A Python domain core with a thin FastAPI JSON layer (`backend/`) and a SvelteKit
SPA (`frontend/`) -- see ARCHITECTURE.md for the full design. The core is
UI-agnostic (no web-framework imports), which is what made the frontend swappable.

Two invariants the file layout does not show:
- `db.py` owns every write (`@_write`: one transaction, logged, re-exports the
  `.sql` on success; validation failures raise `InventoryError`). `api.py` owns
  no domain logic -- it only shapes requests/responses and maps `InventoryError`
  to HTTP 400.
- Detail pages cross-link heavily to related entities. Reverse lookups needing a
  join have a dedicated route -- `GET /parts/{id}/purchase-orders`,
  `/parts/{id}/used-in`, `/parts/{id}/builds|consumed-by`,
  `/suppliers/{id}/parts|purchase-orders`,
  `/supplier-parts/{id}/purchase-orders`; everything else filters an existing
  list client-side.

## Design decisions

- The project was a plugin-based command-log kernel (event sourcing, then snapshot undo/redo) until 2026-07; it was deliberately collapsed to this monolith to iterate on real features first. The old design lives in git history; refactor toward it only when a real feature demands it (e.g. bring the command log back the day a booking needs undo), not speculatively.
- `inventory.sql` is the truth *and the only path the user configures* (`db.data_file` in `settings.toml`); SQLite is an implementation detail. `db.init(sql_path)` builds a scratch `.db` under `tempfile.gettempdir()/stronghold/` (named `<stem>-<sha256 of the .sql's absolute path>[:12]`, so datasets never collide), replays the `.sql` into it, and never writes a `.db` next to the data -- rollback is `git checkout` + restart. Rebuild is ~0.4s on 1.8MB vs the ~1.9s `refresh_all_prices` already costs, so it is not worth caching. `db._db_path` holds the working path (tests assert on it). The export is written atomically (it is the only copy) and omits NULL columns plus `_DERIVED_COLUMNS` (the stock price caches, rebuilt by `refresh_all_prices` at startup); only NULLable columns may be listed there, enforced by a module-level check, since our NOT NULL defaults are Python-side. `Part.estimated_price`/`BuildLine.unit_price` stay in the export -- hand-set for virtual parts, not recomputable. There is no `export_sql` setting (disabling the export would lose every write on restart), and `settings.RENAMED` makes the removed `db.db_path` key fail loudly instead of being ignored. A bulk loader calls `db.suspend_export()` and MUST end with `db.export(force=True)` -- the suspension flag makes a plain `export()` a silent no-op (this bug once made `migrate_inventree` write nothing); `db.init` resets it so a suspension cannot leak past a re-init.
- Data is versioned, and migration is about the *file*, not the database. `db.init` rebuilds the working `.db` from the `.sql` at every startup, so `create_all` always sees the current schema -- what can be stale is the replayed *data*. The asymmetry that matters: a column **added** since the file was written replays fine and silently takes its default (the dangerous case, and it is what a `git checkout` rollback hits); a column **removed/renamed** fails loudly on restore -- the old file's `INSERT`s name a column that no longer exists, killing startup *before* `_migrate` runs. Removal is handled by `db._DROPPED_COLUMNS` (keyed by the version that dropped them): `_import_sql` re-adds each one before the replay so the old `INSERT`s fit, and the matching `_MIGRATIONS` step drops it again. The scaffold is unconditional -- the stamp is only readable once the data is in -- which is free for a current file. Renames are still unhandled; do them as a drop plus an add. So `db.export` stamps every file (a `--` header comment plus `schema.version`/`app.version` rows in the `settings` table -- app metadata, deliberately NOT in `DOMAIN_DEFAULTS`, so `get_setting`/`set_setting` reject them and they stay off the settings page), and `db._migrate` runs after the replay: an older file is upgraded through `db._MIGRATIONS` (keyed by the version each step produces; step 2 drops the stored order references, step 3 converts the enum columns from text to int codes) and re-exported, an unstamped file is treated as version 1, and a **newer** file raises `DataVersionError` and exits 1 -- this app exports only the columns it knows, so one write would drop the rest and `auto_commit` would commit that loss. Two numbers, moving at different rates: `SCHEMA_VERSION` (hand-maintained int in `backend/version.py`, bump only when the data shape changes) and `APP_VERSION` (the git tag via `hatch-vcs`). Only the bare `X.Y.Z` (`RELEASE_VERSION`) is stamped -- the full version carries a `.devN+g<hash>.d<date>` suffix that would rewrite and re-commit the data file on every dev build. See ARCHITECTURE.md "Data versioning".
- No hard deletes. Parts, suppliers and supplier parts carry an `active` flag (deactivated, never removed; UIs hide inactive by default). Purchase orders and build orders have no `active` flag -- their `status` field carries lifecycle state (e.g. `Cancelled`, `Complete`). Stock items likewise use `status` instead of `active`: `available` or `consumed` (`models.StockStatus`) -- stock never disappears (see build consumption below). Those enum *values* are the wire format (JSON and the frontend picklists); what goes **on disk is a small int**, mapped by `models.EnumCode` via the `*_CODES` dicts next to each enum -- so no display text is stored anywhere, and rewording is never a migration. The same applies to `price_basis` and to PO/build `status`. The code maps are append-only: renumbering a member silently reinterprets every row already written. `EnumCode.UNSET` (0) is the empty status POs and builds start with, which is not an enum member. Plain FKs, no cascade. PO lines and BOM lines are order/build detail: plainly removable (a PO line only if not booked).
- Every master record has an integer PK (`Part`, `Supplier`, `SupplierPart`, `PurchaseOrder`, `StockItem`, `POLine`, `BuildOrder`): a local max+1 id in normal use, but the InvenTree pk copied verbatim during migration (the db is empty then, so ids stay traceable back to InvenTree). `sku` (on `Part` and `SupplierPart`) is a plain human code, not unique. Since order codes are derived, search has no column to match them against: `api._ref_id_match` parses a fully-spelled code (`PO-0042`, `po-42`) to the id it names, while a bare number stays unmatched (search is by text, never by id). `Part.assembly` marks a part built from others; its components live in `BomLine(parent_part_id, component_part_id, quantity)` (float qty, unique per parent+component). `Part.virtual` marks a part with unlimited stock (e.g. labour): it never has a stock item, is only used for BOM pricing, and builds never consume it; `assembly` and `virtual` are mutually exclusive (validated in `set_part_assembly`/`set_part_virtual`). A `PurchaseOrder` has a `supplier_id` and a NOT NULL `start_date`, defaulted to today in `create_po` -- it is the sort key for "latest price", so a dateless order could never win it, and `edit_po` rejects blanking it. Order codes (`PO-0042`/`BO-0042`) are **derived from the pk** by `models.po_ref`/`build_ref`, never stored: they were always a copy of the pk, so a stored column only allowed editing them into something that lied. They are still on the output DTOs (computed) but absent from every input DTO, so they cannot be set or patched. `supplier_reference` is unaffected -- that is the supplier's own code and stays editable. A `POLine` references a `supplier_part_id` (whose supplier must match the PO's) and tracks `received` (ordered units received into stock); `edit_po_line` changes its quantity and/or price, repricing the part and any stock booked against that line. Receiving a line (`book_po_line`) creates a stock item counting `received_qty * supplier_part.pack_qty` (a line orders packs; each holds `pack_qty` items), stamps that stock's `po_id`, increments the line's `received`, and adds a `Booking` row -- all in one transaction. `StockItem.count` is float (parts may be measured, e.g. kg/m); `StockItem.po_id`/`StockItem.build_id`/`StockItem.consumed_by_build_id` are nullable FKs to the PO it was received against / the build that produced it / the build that consumed it (separate columns: assembly output produced by one build and eaten by another is both, and collapsing them loses the producing link). Over-receiving (received > ordered) is allowed. Money is float.
- A `BuildOrder(part_id, quantity, status, ...)` is the assembly analogue of a PO: it builds an assembly `Part` (which must have `assembly=True`). `quantity` is an int -- assemblies are whole, no partial builds (produce quantity is likewise int). It is produced incrementally: `produce_build(build_id, qty)` reads the build's **`BuildLine` snapshot** -- the part's BOM copied onto the build at creation, so editing the BOM afterwards never rewrites what an existing build consumes; the snapshot also carries `unit_price` for virtual components only (never consumed, so nothing else records the labour rate the build was costed at), falling back to the part's current estimate when null; the InvenTree import stamps it from the part's price of the day, since InvenTree stores no price on `/build/line/` and its `bom_item` pricing is live, not historical -- and, in one transaction, consumes components FIFO for exactly `qty` units then produces one Available stock item of the assembly counting `qty` and stamped `build_id`. Consumption never destroys stock: a source Available item's count drops by the amount taken and a matching `STOCK_CONSUMED` item (also stamped `build_id`, and carrying the source's `po_id` for price provenance) is split off -- so what was used, and the price it was bought at, stay traceable (the basis for recalculating produced cost). Virtual components hold no stock, so nothing is drawn down, but a `STOCK_CONSUMED` row is recorded for them at the build line's snapshotted rate (`PriceBasis.VIRTUAL`) so the labour shows in the consumed table and counts in `build_unit_cost`; being consumed rows they never enter the stock value total. Shortages do not block production: a short component is drained to zero and the missing quantity is put on credit -- a `STOCK_CONSUMED` row at the part's estimate (so the assembly is costed in full rather than as a floor) plus a **negative-count `STOCK_AVAILABLE` row** stamped `consumed_by_build_id`, written as an adjacent id pair (consumed first). This is the one place Available stock goes negative; the debt nets out of on-hand sums and is deducted from the stock value report. `produce_build`'s FIFO select therefore filters `count > 0` -- consuming a debt row would invert the arithmetic. Booking the missing parts on a PO settles it (`_settle_stock_debt`, called from `book_po_line`): the debt shrinks, the paired consumed row is stamped with the PO and repriced to what was paid (splitting if the receipt only covers part of it), the settled units never reach the shelf, and the build's produced stock is repriced off the now-real cost. `settle_debt_from_stock(debt_id, qty, item_id=None)` (POST `/stock/{id}/settle`) is the manual counterpart for a part that ended up holding both a debt row and available stock: it draws the sources down FIFO (or off one named item, like a stocktake), shrinks the debt and the paired placeholder, and writes one consumed row per source carrying that source's own price -- so the build is repriced off what the shelf stock actually cost rather than the estimate. Both settlement paths depend on the adjacent-id pairing, so anything writing a debt must keep emitting the consumed row first. Debt rows settle to zero rather than being deleted; the settled receipt row also ends at zero (its units went straight into the assembly and it must survive because it carries the `Booking`), so the stock tables carry a `nonzero` bool filter hiding zero-count rows by default -- do not "fix" those zeros by keeping counts on the shelf, that double-counts against the assembly they went into. The user chose to produce anyway; the frontend surfaces the shortfall in the produce dialog. `produced_qty(build_id)` sums every row the build produced (not just Available ones -- output sold on or eaten by a later build is still output), floored at `BuildOrder.imported_produced` (InvenTree's own `completed` count, imported because InvenTree deletes fully-used stock, so surviving rows cannot reconstruct history); when cumulative production reaches `build.quantity` the status flips to `Complete`. Producing more than remaining is rejected, as is lowering `quantity` below what's already produced. Status transitions are constrained in `edit_build`: `Complete` only when produced equals quantity, and once anything is produced the order is locked to `Production`/`Complete` (no reverting). The produce button in the UI shows only when `status == "Production"`; the status dropdown greys out disallowed transitions. `BuildStatus` is mostly InvenTree's labels with two departures: `Draft` (ours -- the status `create_build` defaults to via `BuildOrderIn`, a scratchpad that books no demand) and no `On Hold`, which the InvenTree import folds into `Pending`. Demand (`db.part_demand`, see below) counts `Pending` and `Production` builds; because the frontend validator generator keys enum picklists by field name (last write wins), PO, build and stock `status` collapse into one generated `STATUS_OPTIONS` -- stock's wins -- so both the PO and build picklists are hardcoded in `frontend/src/lib/status.ts` (`PO_STATUS_OPTIONS`/`BUILD_STATUS_OPTIONS`), never imported from `validators.ts`. Any new DTO with a `status` field silently changes which one wins.
- InvenTree import is a one-shot migration, not a product feature. `backend/migrate_inventree.py` (run `uv run python migrate_inventree.py <url> <user> <password> --data-file PATH`; `--data-file` is required and has no default, since the run deletes it) drops the data file and rebuilds it: parts, BOM, suppliers, supplier-parts, purchase orders (cancelled ones and their lines dropped), PO lines, build orders (cancelled dropped), each build's component snapshot (InvenTree `/build/line/`, whose extended quantity is divided by the build quantity to give our per-unit `BuildLine`; virtual components get `unit_price` baselined at the part's current price, as InvenTree has no historical rate to import), the stock each build consumed (InvenTree's `?consumed=true` stock, imported as `STOCK_CONSUMED` rows stamped `build_id` so historical builds can be costed) with produced stock back-linked from InvenTree's own `build` field on the stock row, and available stock (fetched directly, not replayed as bookings). Every InvenTree pk is copied as our pk, so no remap and no `inventree_id` column. Rows whose FK targets are missing (or fractional stock qty) are skipped/rounded with a printed report; a fractional build-order quantity is bad data (assemblies are whole) and aborts the import with an error rather than being rounded. `backend/inventree.py` is the read-only HTTP client it uses. **Do not maintain it against versioning/schema changes.** It was a one-time operation and is unlikely to be run again: it is exempt from the data-versioning rules above, and a schema change does not oblige you to update it. It drops the data file and calls `db.init` on the result, so it always starts current anyway. If it ever breaks, fix it when someone actually needs it -- do not spend effort keeping it current speculatively.
- Settings split by one test: does a wrong value stop the app running/being reachable? Deployment settings live in `settings.toml` (`settings.py`); domain settings (GUI title, stocktake reason lists) are data in the `settings` table (`db.DOMAIN_DEFAULTS`, `db.get_setting`/`db.set_setting`), edited on `/settings`. A setting holding a list is one comma-separated string (`stocktake.add_reasons`/`subtract_reasons`), parsed by the route that serves it (`GET /api/settings/stocktake-reasons`) rather than by the frontend. The whole InvenTree connection (url/username/password) goes in `settings.toml`, never the database: `inventory.sql` is tracked in git. `db.auto_commit` (default false, passed to `db.init`) makes `export()` end with `git add`+`git commit` in the data file's own directory, message = the newest `Activity` row *if it is newer than the last one committed* (`db._committed_activity_id`) -- otherwise `db._NO_ACTIVITY_MESSAGE`, since a write that logs nothing would otherwise reuse the previous write's message. Git failures (no repo, no identity) are logged at DEBUG and ignored; `db.init` raises if auto_commit is on for a data file inside the app repo. Two bookends around that: `db.init` calls `_commit_pending_changes()` **before** the replay (startup ends in an export that overwrites the file, so an uncommitted hand edit -- or a write from a session that died before committing -- would otherwise be destroyed silently; it is committed under `db._UNCOMMITTED_MESSAGE` instead), and `main._lifespan` exports once on shutdown. Startup's own export is not a domain write, so `_startup_message` (set around `init`'s `export()`, honoured by `_commit_export`) supplies a message describing what startup did -- stamping the version, migrating, or just opening. Without it the newest `Activity` row was reused, producing a duplicate commit named after an unrelated earlier change (`_committed_activity_id` resets in `init`, so that row always looks fresh). The shutdown export is belt-and-braces only: every write already exports and commits, so nothing is pending even after a `SIGKILL` -- do not add in-memory buffering that would make it load-bearing.
- `PartOut` carries four derived quantities, none of them cached: `in_stock` (a grouped sum of `STOCK_AVAILABLE` counts, so debt rows net out), `needed` and `incoming` from `db.part_demand`, and `suggested_order` = `max(0, needed - in_stock - incoming)`. `part_demand` is two grouped queries plus one `produced_qty` per open build: demand is each `Pending`/`Production` build's `BuildLine` per-unit quantity times its units left to produce (virtual components excluded -- they hold no stock); incoming is `(POLine.quantity - received) * pack_qty` over non-terminal PO statuses. The part page's purchase dialog prefills packs as `ceil(suggested_order / pack_qty)` *per supplier part*, since pack sizes differ.
- `Part.estimated_price` is a cached unit price (`price_partial` flags an incomplete BOM), computed in `db.py`'s pricing section, not in `api.py`. A virtual part's price is hand-set (`set_part_price`, PATCH `estimated_price`; rejected for non-virtual parts, and `patch_part` uses `model_fields_set` so an explicit null clears it) and returned as-is by `_compute_price`; a non-virtual, non-assembly part is worth `latest_po_unit_price` (the newest non-cancelled PO line pricing it, `price / pack_qty`, ordered by `PurchaseOrder.start_date` -- ids do not follow date order); an assembly is the recursive sum of its BOM components. `POLine.price` is not nullable, so `0` means "not filled in" and never counts as a price. The cache is refreshed inside the transaction of every write that can change it (`add_po_line`, `remove_po_line`, the BOM writes, `edit_supplier_part`, `set_part_assembly`, `edit_po`) via `refresh_part_price`, which walks *up* to every containing assembly; `refresh_all_prices` (POST `/api/parts/refresh-prices`, and once in `main.create_app` at startup) is the backfill path, covering rows written outside the app.
- `StockItem.unit_price` is a *separate* cache from `Part.estimated_price` and the two differ by design: stock is worth what its own order paid, the part is worth its latest price. `db.refresh_stock_price` resolves one item -- its PO (the booked line, else that order's line for the same part) first, then its producing build (`build_unit_cost`: the sum of what that build's `STOCK_CONSUMED` rows were worth, divided by `max(produced_qty, build.quantity)` -- output gets sold on, so surviving units must not inherit the whole batch cost), then the part estimate, recording which in `StockItem.price_basis` (`models.PriceBasis`: `po`/`build`/`build_partial`/`estimate`/`po_no_price`/`none`; `build_partial` means a consumed input was itself estimated -- which covers a shortage, since the missing quantity is consumed at the part's estimate until the parts are received). Refreshed by the writes that create or reprice stock (`book_po_line`, `book_po`, `create_item`, `produce_build`) and by `refresh_part_price` for every part it touches. The stock value report is a plain read of these columns -- it owns no pricing logic. Its `total`/`unpriced` cover `STOCK_AVAILABLE` rows only: consumed rows are build inputs already counted inside the assembly they became, so summing them would double-count (they stay in `rows` for provenance). BOM cycles are not blocked on write (see `add_bomline`), so the recursive walk carries a path-scoped `seen` guard.
- Assemblies are built, not purchased: `create_supplier_part`/`edit_supplier_part` reject an assembly part, and `set_part_assembly` rejects a part a supplier already sells. `Part.purchasable` (default true) is the manual version of the same gate -- `_check_purchasable` rejects a supplier part for an assembly *or* a part flagged non-purchasable, so only a purchasable part can reach a PO.
- Every write should append an `Activity` row (`db._activity`, inside the caller's transaction so it commits atomically), surfaced by `GET /api/activity` and the `/activity` page. `refs` is a JSON list of `{type, id, label}` for cross-linking. **Any new write function gets one** -- with `auto_commit` on, the message is also the git commit message, so a write that logs nothing commits under `db._NO_ACTIVITY_MESSAGE` ("worth reporting to the developers"). Edits log only what actually changed (`db._field_changes` renders `field old -> new` per changed attribute) and log nothing when nothing changed, so a no-op PATCH does not manufacture a row. Coverage is still not total (trivial single-field setters like `edit_part`/`set_part_sku` don't log yet); add a call when you touch one.
- Deliberate shortcuts are marked with `ponytail:` comments naming the ceiling and upgrade path.

## Commands

- `uv run pytest` -- run backend tests (`backend/test_domain.py` + `backend/test_api.py`)
- Frontend needs Node 20+ (Node 18 builds but is unsupported); the dev server proxies `/api` to :8080
- Prod (single process): build the frontend, then `cd backend && uv run main.py <settings.toml>` serves API + SPA on :8080. The settings path is a required argument and every relative path inside the file resolves against *its own directory* (`Settings.path_of`), not the cwd. Running `uvicorn main:app` directly skips `db.init`, so the API 500s -- use `main.py`
- Frontend DTO types + validators are generated from the backend: `cd frontend && npm run gen:types` regenerates `backend/openapi.json` from the live routes (`backend/export_openapi.py`), then writes `frontend/src/lib/api-types.ts` (openapi-typescript) and `frontend/src/lib/validators.ts` (valibot schemas via `scripts/gen-validators.mjs`). `src/lib/types.ts` is thin friendly aliases over api-types; form validation uses the valibot schemas through `src/lib/validate.ts`. After changing any DTO or adding a Pydantic `Field(...)` constraint in `backend/api.py`, run `gen:types` -- validation rules live in the Pydantic models only. `openapi.json` is gitignored (a build artifact); `api-types.ts`/`validators.ts` are committed so the frontend builds without a live backend.
- `backend/version.py` holds `SCHEMA_VERSION` (hand-maintained; bump + add a `db._MIGRATIONS` step when the data shape changes -- and, if the change *removes* a column, a `db._DROPPED_COLUMNS` entry too, or old files stop opening), `APP_VERSION` (from the git tag) and `RELEASE_VERSION` (bare `X.Y.Z`, the one stamped into data files). The project is a real package now (`[build-system]` + `hatch-vcs` in `pyproject.toml`), so **after tagging, run `uv sync --reinstall-package stronghold`** or the version stays stale -- it is resolved at install time, not read live. Plain `uv sync` is not enough: with `pyproject.toml` unchanged it just audits the existing install and silently leaves the old version in place.
- Navigate the two big backend files by section banner, don't read them whole: `grep -n '^# --' backend/db.py` (or `api.py`) is a working table of contents. Two traps: five Pydantic models sit *outside* `api.py`'s `# -- schemas` section, so `grep -n '^class .*BaseModel' backend/api.py` is the reliable way to find them all; and `db.py`'s `set_part_assembly`/`set_part_virtual`/`set_part_purchasable`/`set_part_price` live under `# -- bom`, not `# -- parts`.
- A tracked pre-commit hook (`.githooks/pre-commit`) blocks commits with stale generated files when any `backend/*.py` (not just `api.py` -- `models.py` holds the StrEnums that become picklists), `api-types.ts`, or `validators.ts` is staged. It is not active in a fresh clone -- enable once with `git config core.hooksPath .githooks`.
- CI (`.github/workflows/ci.yml`) runs on every PR: `pytest`, `ruff check`, `ruff format --check`, `npm run check` (svelte-check), and `npm run check:types-fresh`. That last one regenerates from the live routes and fails on any diff, so stale generated types are caught whichever backend file caused the drift.
- Secrets (InvenTree URL/username/password for `migrate_inventree.py`) live in `SECRETS.md` at the repo root (gitignored). Read credentials from there when a task needs them; never commit, echo, or otherwise expose the file's contents.

## Running the app for manual verification

- Free port 8080 before restarting: `ss -ltnp | grep :8080` for the pid, then `kill -9 <pid>`. Never `pkill -f main.py` -- it can kill the agent's own process tree.
- The frontend renders client-side (SPA), so a 200 on `/parts` only proves the SPA fallback served. **Exercise real flow via the API** (`curl /api/parts`, POST/PATCH) and/or drive the DOM with the browser tools -- screenshots may be flaky, so read state via the JS tool (`document.querySelectorAll('tbody tr').length`, `.rowcount`).
- The API is the contract: `curl http://localhost:8080/api/...` is the fastest proof a change works end-to-end.

## Testing

- Happy-flow coverage only -- not 100% line/branch coverage as a goal in itself. This is a **deliberate override** of the user-wide ">=1.0.0 targets 100% coverage" rule, decided when 1.0 was tagged, not an artefact of being pre-1.0: this is a single-user tool whose real risks are caught by integration tests over real flows, and chasing 100% would invite exactly the defensive/dead code the same rules ban. Do not re-open it at the next tag.
- Do not add edge-case tests speculatively. Add one only after a real bug is found there, to prevent regression.
- Frontend correctness is checked with `npm run check` (svelte-check) and by driving the running app -- there is no frontend test runner.
- Backend lint/format is ruff (`uv run ruff check backend`, `uv run ruff format backend`), config in `pyproject.toml`. `S`/`BLE` are enabled because the codebase carries `noqa` for them; `DTZ011` is off (PO `start_date` is a calendar sort key, not an instant). Both are CI gates, so run them before committing.

The user-wide `~/.claude/CLAUDE.md` sets general coding conventions (Python style, git workflow, etc.) and applies here too. Where this file conflicts with it, this file wins.

## Commits
Never commit to `main`. Every change goes on a feature branch and reaches
`main` through a PR (`gh pr create`) -- see the README's Contributing section.
Commit isolated changes one by one. Released at 1.0: breaking changes need a
major version bump and must be named in the PR description. Releases are cut by
tagging (`git tag -a v1.2.3` on `main`, then `uv sync --reinstall-package stronghold`) -- there is no version
number to edit by hand; see the README's Releases section.
